How the Trajectory Library Works

You wrote the MATLAB trapezoidal profile. This document walks through every piece of C++ and math added on top of it — building from what you already know, step by step. Free study references at the bottom.

Part 1 C++ in Five Minutes for a Motion Engineer

In MATLAB you call functions directly. In C++ for real-time systems, you organize code into classes — bundles of data and functions that belong together. A motion profile is a good example: it has internal state (the phase timing) and behaviors (plan, evaluate). A class holds both.

What a class looks like

Think of a class like a function block in IEC 61131-3 PLC programming — it has inputs, outputs, and internal memory that persists between calls.

class TrapezoidalProfile {
public:
    bool  plan(float q0, float qf, const TrajectoryLimits& limits);
    bool  evaluate(float t, float& pos, float& vel, float& accel);
    float getDuration();

private:
    float _t1, _t2, _t3;    // phase timing — stored between calls
    float _vPeak, _aMax;
    bool  _valid;
};

public: means these functions are accessible from outside. private: means only the class itself can touch those variables — they're internal state.

Interfaces — the really important concept

Suppose you want to swap between a trapezoidal profile and an S-curve profile without changing the code that uses the profile. You need a contract — a guarantee that both types respond to the same function calls. In C++ this is an interface (also called an abstract class).

⚙️ Motion Control Analogy

This is exactly like a CiA 402 drive profile. Whether you're talking to a Beckhoff EL7211, a Kollmorgen AKD, or a simulated axis, they all respond to the same CoE objects: target position, actual position, status word. The interface is standardized; the implementation is swappable. ITrajectoryProfile plays the same role for trajectory generators.

class ITrajectoryProfile {
public:
    virtual ~ITrajectoryProfile() = default;

    virtual bool  plan(float q0, float qf, const TrajectoryLimits& limits,
                       float targetDuration = 0.0f) = 0;
    virtual bool  evaluate(float t, float& pos, float& vel, float& accel) const = 0;
    virtual float getDuration() const = 0;
};

The keyword virtual marks a function that can be overridden by a derived class. The = 0 means "this class does NOT implement it — any concrete class must." You can never create an ITrajectoryProfile object directly; it is abstract.

TrapezoidalProfile then implements the interface:

class TrapezoidalProfile : public ITrajectoryProfile {
public:
    bool  plan(...)     override;   // fills in the abstract promise
    bool  evaluate(...) override;
    float getDuration() override;
    ...
};

The override keyword tells the compiler "I intend to override a virtual function." If you mistype the name, the compiler catches it — it won't silently create a new, unrelated function.

Pointers — holding a reference without knowing the type

A pointer (ITrajectoryProfile*) holds the memory address of an object. The crucial thing: a pointer to the interface type can hold the address of any concrete type that implements it. This is called polymorphism.

TrapezoidalProfile trap;          // the real object
ITrajectoryProfile* p = &trap;    // pointer to the interface

p->plan(0, 10, limits);           // calls TrapezoidalProfile::plan()
p->evaluate(0.5, pos, vel, accel); // calls TrapezoidalProfile::evaluate()

// Later you can point at a different implementation with no other code changes:
// SCurveProfile scurve;
// p = &scurve;                    // now jerk-limited, nothing else changes

TrajectoryGroup and CartesianMove store ITrajectoryProfile* pointers — they call plan() and evaluate() without knowing or caring whether a trapezoidal or S-curve profile is behind the pointer.

Part 2 From MATLAB to C++ — What You Already Know

You wrote the MATLAB trapezoidal trajectory math. The C++ port is the same math, reorganized. Here is the direct mapping:

MATLAB functionC++ equivalentNotes
Trap_calculateTimeSegments First half of TrapezoidalProfile::plan() Computes _t1, _t2, _t3, _vPeak
Trap_calculateMotion Kinematic equations inside evaluate() s = s₀ + v₀·dt + ½a·dt² used per phase
Trap_calculateInitialConditions Inlined into evaluate() Phase entry conditions recomputed each call (no array storage needed)
Trap_CalculateTraj (the loop) TrapezoidalProfile::evaluate() Same phase-selection logic; C++ computes one point per call
getTrapTraj (top-level) plan() + repeated evaluate() calls from the caller C++ caller drives the loop; library just answers point-in-time queries
Key Difference

MATLAB generates the entire trajectory as an array upfront — all points, all at once. The C++ library computes one setpoint on demand, called every control tick. This is what makes it real-time safe: no pre-allocation, no loops in the hot path, just arithmetic.

The phase selection — straight from your MATLAB

Your MATLAB Trap_CalculateTraj uses this branching:

if t(R) < segments.t1
    % acceleration phase
elseif t(R) < segments.t2
    % cruise phase
elseif t(R) < segments.t3
    % deceleration phase
else
    % settled
end

The C++ evaluate() does exactly the same thing:

if (t < _t1) {
    // acceleration — same kinematic equation as your Trap_calculateMotion
    pos   = _q0 + 0.5f * a * t * t;
    vel   = a * t;
    accel = a;
} else if (t < _t2) {
    // cruise
    float dt = t - _t1;
    pos   = s1 + v1 * dt;
    vel   = v1;
    accel = 0.0f;
} else {
    // deceleration
    float dt = t - _t2;
    pos   = s2 + v1 * dt - 0.5f * a * dt * dt;
    vel   = v1 - a * dt;
    accel = -a;
}

Time-dilation (the targetDuration parameter)

Your MATLAB didn't have this, but it uses the same math you already wrote. When you want a profile to take exactly T seconds instead of its natural minimum time, the peak velocity must be lower. Setting t₃ = T and solving for vPeak:

t₃ = vPeak/aMax + displacement/vPeak Rearrange: vPeak²/aMax – T·vPeak + displacement = 0 Quadratic formula (take the smaller root — lower speed, longer move): vPeak = (aMax / 2) × (T – √(T² – 4·displacement/aMax))

This is what TrajectoryGroup uses to slow down the faster axes to match the slowest one.

Part 3 Vec3 — The 3D Building Block

A Vec3 is simply a container for three floats — an (x, y, z) coordinate or direction — with math operations defined so you can write p0 + dir * s instead of operating on each component individually.

struct Vec3 {
    float x = 0.0f, y = 0.0f, z = 0.0f;

    Vec3 operator+(const Vec3& o) const { return {x+o.x, y+o.y, z+o.z}; }
    Vec3 operator*(float s)       const { return {x*s,   y*s,   z*s};   }
    float dot(const Vec3& o)      const { return x*o.x + y*o.y + z*o.z; }
    Vec3  cross(const Vec3& o)    const { ... }
    Vec3  normalized()            const { return *this / magnitude(); }
};
⚙️ Motion Control Analogy

Think of Vec3 like the three channels of a 3-axis encoder head — X, Y, Z readings bundled together. The math operations (add, subtract, scale) are the arithmetic you'd do on those readings to compute distances and directions.

Dot product — measuring alignment

a · b = ax·bx + ay·by + az·bz = |a| × |b| × cos(angle between them)
  • Result = 1 → vectors point the same direction
  • Result = 0 → vectors are perpendicular (90°)
  • Result = −1 → vectors point opposite directions

Used in Quatf::slerp() to measure the angle between two orientations.

Cross product — finding a perpendicular direction

a × b = ( ay·bz – az·by, az·bx – ax·bz, ax·by – ay·bx )

The result is a vector perpendicular to both a and b. Used in ArcPath to build the arc's coordinate frame: given a radial direction u and the arc plane's normal, normal × u gives the tangent direction at the start of the arc.

Normalize — making a direction vector unit-length

Many calculations require that direction vectors have a magnitude of exactly 1 (a "unit vector"). If a vector has length 3.7, dividing each component by 3.7 scales it to length 1 without changing the direction. The tangent returned by LinePath and ArcPath is always normalized so that speed × tangent gives the correct velocity magnitude.

Part 4 Quaternions (Quatf) — Representing 3D Orientation

Why not just use three angles?

Euler angles (roll, pitch, yaw) seem intuitive but have a famous problem called gimbal lock: at certain orientations, two of the three rotation axes align and you lose a degree of freedom. This causes singularities in interpolation — the end-effector snaps or spins unexpectedly. Industrial 6-axis robots hit this when the wrist is near-straight.

Quaternions avoid this completely. They represent any rotation in 3D without singularities.

What a quaternion stores

A quaternion (w, x, y, z) encodes a rotation as:

w = cos(angle / 2) x = sin(angle / 2) × axis_x y = sin(angle / 2) × axis_y z = sin(angle / 2) × axis_z

Example: a 90° rotation about the Z-axis:

angle = 90°, axis = (0, 0, 1) w = cos(45°) = 0.7071 x = sin(45°) × 0 = 0 y = sin(45°) × 0 = 0 z = sin(45°) × 1 = 0.7071 Quaternion: (0.7071, 0, 0, 0.7071)

You don't need to construct quaternions by hand for this library. You receive them from a sensor or kinematics solver, store them in Quatf, and pass them to CartesianMove.

SLERP — smooth interpolation between two orientations

SLERP (Spherical Linear Interpolation) is to quaternions what linear interpolation is to numbers. Given a start orientation q0, an end orientation q1, and a fraction t ∈ [0, 1]:

SLERP(q0, q1, 0.0) → q0 (start) SLERP(q0, q1, 0.5) → midpoint rotation SLERP(q0, q1, 1.0) → q1 (end)

The result always rotates at constant angular velocity along the shortest path between the two orientations — no snapping, no gimbal lock.

static Quatf slerp(Quatf a, Quatf b, float t) {
    float d = a.dot(b);
    if (d < 0.0f) { b = {-b.w,-b.x,-b.y,-b.z}; d = -d; }  // shortest path

    if (d > 0.9995f)   // nearly identical — fall back to linear interpolation
        return lerp(a, b, t).normalized();

    float omega  = acosf(d);           // angle between quaternions
    float sinOmg = sinf(omega);
    float s0 = sinf((1.0f - t) * omega) / sinOmg;
    float s1 = sinf(       t   * omega) / sinOmg;

    return { s0*a.w + s1*b.w,  s0*a.x + s1*b.x,
             s0*a.y + s1*b.y,  s0*a.z + s1*b.z };
}
⚙️ Motion Control Analogy

SLERP is the rotational equivalent of your trapezoidal profile's cruise phase — constant-rate motion from start to end. The difference is that SLERP interpolates orientation (where you're pointing) rather than position (where you are). In CartesianMove, orientation is SLERPed by how far along the path you've travelled, not by time — so if you pause mid-move, the wrist orientation also pauses at the correct intermediate rotation.

Part 5 Arc-Length Parameterization — Separating Geometry from Timing

This is the conceptual heart of the Cartesian system. Before writing any path code, we need to understand one key idea.

The insight

Your trapezoidal profile solves a 1D problem:

"Given a scalar distance to travel, produce a smooth speed vs. time profile."

It doesn't know or care where that distance is in space. All it knows is: start at 0, end at length, obey vMax and aMax.

IPathGeometry solves a completely different problem:

"Given a distance travelled along a path, what is the 3D position and direction at that point?"

The input to both is the same number — arc length s, the odometer reading along the path. This common currency lets you combine any timing with any geometry.

⚙️ Motion Control Analogy

You probably know cam profiles. A cam profile maps cam angle → follower position. The cam angle is the independent variable (like our s), and the follower position is the output. Separately, the cam shaft speed (rpm) controls how fast the angle advances — that's the timing. You design the cam shape independently of how fast you spin it. This library does exactly the same thing: the path shape (IPathGeometry) is designed independently of the speed profile (ITrajectoryProfile).

class IPathGeometry {
public:
    // s ranges from 0 to getLength().
    // Returns Cartesian position and unit tangent direction at arc-length s.
    virtual void evaluate(float s, Vec3& position, Vec3& tangent) const = 0;

    virtual float getLength() const = 0;
};

The tangent is the direction you're travelling at point s. For a straight line, it's constant. For a circle, it rotates continuously as you move along the arc.

Part 6 LinePath — Straight Line in 3D

A straight line from point p0 to point p1 is the simplest path geometry. Given arc length s, the position is:

position(s) = p0 + direction × s where direction = (p1 – p0) / |p1 – p0| (unit vector from p0 toward p1)

The tangent is simply direction — it's the same everywhere on a straight line. Length is the Euclidean distance between the endpoints.

LinePath::LinePath(const Vec3& p0, const Vec3& p1) : _p0(p0) {
    Vec3 delta = p1 - p0;
    _length = delta.magnitude();
    _dir    = (_length > 0.0f) ? delta / _length : Vec3{1,0,0};
}

void LinePath::evaluate(float s, Vec3& position, Vec3& tangent) const {
    position = _p0 + _dir * s;
    tangent  = _dir;
}

That's the entire class. No interesting math — just the definition of a line.

Part 7 ArcPath — Circular Arc in 3D

This is the most math-heavy piece. Let's build it up from scratch.

Step 1 — A circle needs a coordinate frame

A circle in 3D space lives in a plane. To describe points on it, you need two perpendicular unit vectors that lie in that plane. Call them u and v.

Then any point on the circle is:

position(θ) = center + radius × (cos(θ) · u + sin(θ) · v)

At θ = 0: position = center + radius × u — this is the start point.

So u is the unit vector from the center toward the start point:

u = (startPoint – center) / radius

Step 2 — Finding v with the cross product

You want v to be perpendicular to u and lie in the arc's plane. The arc plane's orientation is defined by its normal vector (pointing out of the plane, like the Z-axis of the arc's local frame).

v = normal × u (cross product)

Why does this work? The cross product of two vectors produces a vector perpendicular to both. Since normal is perpendicular to the arc plane, and u lies in the arc plane, their cross product lies in the arc plane and is perpendicular to u.

Right-hand rule check: if normal points out of the page and u points right, then v = normal × u points upward — which is the CCW tangent direction at the start. ✓

Step 3 — Arc length to angle

The arc length of a sector is s = radius × θ, so:

θ(s) = sign × s / radius where sign = +1 for CCW sweep, –1 for CW sweep

Step 4 — The tangent (derivative of position)

The tangent is how position changes as you move along the path — mathematically, d(position)/ds. Using the chain rule:

d(position)/ds = d(position)/dθ × dθ/ds d(position)/dθ = radius × (–sin(θ)·u + cos(θ)·v) ← derivative of the circle formula dθ/ds = sign / radius tangent = sign × (–sin(θ)·u + cos(θ)·v)

Verification:

  • At θ = 0 (start): tangent = sign × v — pointing in the CCW direction ✓
  • After a quarter-circle CCW (θ = π/2): tangent = –u — pointing backward along the u-axis ✓
  • After a half-circle CCW (θ = π): tangent = –v ✓
void ArcPath::evaluate(float s, Vec3& position, Vec3& tangent) const {
    float theta = _sign * s / _radius;
    float c = cosf(theta), sn = sinf(theta);
    position = _center + _u * (_radius * c) + _v * (_radius * sn);
    tangent  = _v * (_sign * c) - _u * (_sign * sn);
}

Part 8 CartesianMove — Combining Profile and Path

With the building blocks in place, CartesianMove is straightforward. In plan(), the profile is told to run over [0, path.getLength()] instead of [q0, qf] — arc length replaces joint angle as the 1D coordinate. Everything else in the profile is unchanged.

bool CartesianMove::plan(IPathGeometry* path, const Quatf& q0, const Quatf& q1,
                          ITrajectoryProfile* profile, const TrajectoryLimits& limits) {
    _path    = path;
    _length  = path->getLength();
    _q0 = q0;  _q1 = q1;
    return _profile->plan(0.0f, _length, limits);  // 1D: 0 → total arc length
}

evaluate(t) is three steps:

Step 1 — Ask the profile: how far along the path, and how fast?

float s, speed, tangAccel;
_profile->evaluate(t, s, speed, tangAccel);
// s         = arc length traveled so far (0 → totalLength)
// speed     = ds/dt  (scalar, always positive while moving forward)
// tangAccel = d²s/dt² (scalar, positive=accelerating, negative=decelerating)

Step 2 — Ask the path: given distance s, where are we in 3D?

Vec3 tangent;
_path->evaluate(s, position, tangent);
// position = Cartesian point at arc length s
// tangent  = unit direction of travel at that point

Step 3 — Combine: scalar speed → 3D velocity vector

velocity        = tangent * speed;        // speed (m/s) in the tangent direction
accelTangential = tangent * tangAccel;    // tangential acceleration component

float u     = s / _length;               // 0 at start, 1 at end of path
orientation = Quatf::slerp(_q0, _q1, u); // orientation tracks path position
⚠️ Centripetal Acceleration on Curved Paths

The accelTangential output is only the along-path component of acceleration. On an arc, there is also centripetal (centrifugal) acceleration pointing toward the center: a_c = v² / radius. This is perpendicular to travel and NOT included in what CartesianMove returns. It matters only when computing torque feedforward for dynamics — a future layer will need to account for it. For position/velocity control it is not needed.

Key Insight — Pluggability

Because both IPathGeometry and ITrajectoryProfile are interfaces, you can combine any path with any profile. SCurveProfile plugs in with no changes to CartesianMove. A spline path implementation plugs in with no changes to either profile. The pieces are truly independent.

Part 9 TrajectoryGroup — Synchronizing Multiple Joints

The problem without synchronization

Suppose you command a 3-joint arm from configuration A to configuration B. Joint 1 needs to travel 45°, joint 2 needs 10°, joint 3 needs 90°. With individual profiles at the same limits, each joint finishes at a different time. The arm traces a curved, unpredictable path through joint space because the joints are moving at different fractions of completion at every instant.

The solution: two-phase planning

⚙️ Motion Control Analogy

This is electronic gearing with a virtual master encoder. Each joint is geared to a shared virtual master axis with its own cam profile (the time-dilated trajectory). The master position is time t; each joint's cam maps t → joint position. All joints share the same master and therefore always arrive together — like a synchronized multi-axis CNC move.

Phase 1 — Find the slowest axis:

float maxDuration = 0.0f;
for (int i = 0; i < count; ++i) {
    _profiles[i]->plan(q0[i], qf[i], limits[i]);      // minimum-time plan
    float d = _profiles[i]->getDuration();
    if (d > maxDuration) maxDuration = d;              // find the slowest
}

Phase 2 — Slow everyone down to match:

for (int i = 0; i < count; ++i) {
    _profiles[i]->plan(q0[i], qf[i], limits[i], maxDuration);  // time-dilate
}

The targetDuration parameter in the second call uses the quadratic formula from Part 2 to find a lower vPeak — the axis "cruises more slowly" and fills the extra time with a longer cruise phase. All axes arrive together.

What this does NOT do

It does not make the joints trace a straight Cartesian line. Each joint has its own independent profile shape (determined by its own distance and limits). Even though they're synchronized in time, the intermediate joint configurations still depend on each profile's individual shape. For a straight Cartesian line, you need CartesianMove with LinePath.

Part 10 The Big Picture

Here is how all the pieces relate:

ITrajectoryProfile (interface)
└── TrapezoidalProfile — phase timing, kinematic equations (MATLAB port)
└── SCurveProfile — jerk-limited, 7 segments (MATLAB port)

IPathGeometry (interface)
└── LinePath — straight line, p = p0 + dir×s
└── ArcPath — circular arc, uses u/v coordinate frame

Compositions
└── CartesianMove — IPathGeometry + ITrajectoryProfile → 3D Cartesian setpoints
└── TrajectoryGroup — N × ITrajectoryProfile, synchronized to shared duration

Math types (header-only, no allocation)
Vec3 — 3D position/direction | Quatf — 3D orientation + SLERP

The hot path at every control tick is: call evaluate(t) on whatever top-level object you have (CartesianMove or TrajectoryGroup). Everything is pure arithmetic — no memory allocation, no loops, bounded execution time.
